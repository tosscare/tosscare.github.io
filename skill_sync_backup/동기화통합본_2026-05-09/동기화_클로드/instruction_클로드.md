## §11-J 카톡 자동화 4시나리오 박제 (신설)

**§11-I 다음에 §11-J 신설**:

### §11-J. 토스인슈1 사전레포트 카톡 자동발송 — 4시나리오 정의

본 프로젝트 카톡 자동발송 자동화의 시나리오 분기 표준. mr.와이 본업 운용 시 항상 아래 4시나리오로 분기.

#### 시나리오 4종

| # | 케이스 | 처리 |
|---|---|---|
| 1 | 친구 ❌ (새 번호) | 친구추가 → 노란 1:1 채팅 → 대화창 → 메시지·PNG 발송 |
| 2 | 친구 O (이미 등록) | 친구추가 시도 → "추가할 수 없습니다" 감지 → 팝업 닫기 → 이름 검색 → 1명 매칭 → 더블클릭 → 대화창 → 메시지·PNG 발송 |
| 3 | 동명이인 (검색 결과 2명+) | **미발송 + 오류로그(duplicate_name)** + 다음 고객 |
| 4 | 친구추가 허용 OFF (검색 결과 0명) | **미발송 + 오류로그(friend_add_failed)** + 다음 고객 |

#### 핵심 룰

| 룰 | 내용 |
|---|---|
| 친구추가 시도 우선 | 항상 친구추가부터 시도 — `--no-friend-add` 모드는 PoC 한정 |
| 동명이인 정의 | "정확한 이름 검색 시 결과 영역에 표시되는 친구가 2명 이상". 부분 매칭 포함 |
| 오류 사유 별도 코드 | mr.와이가 후속 처리 다르게 하기 위함 (duplicate_name vs friend_add_failed) |
| 한글이름 매칭 | 이름이 카톡 등록 이름에 포함되면 동일인 처리 (닉네임 변경 ♥·이모지·꾸밈 OK) |
| 메시지 발송 | 텍스트 → 2~6초 랜덤 → PNG (1메시지 ❌, 2메시지 분리 발송) |

## §11-K 카톡 자동화 코드 아키텍처 박제 (신설)

**§11-J 다음에 §11-K 신설**:

### §11-K. 카톡 자동화 코드 아키텍처 — 좌표 ❌·활성 창 트래킹

#### 핵심 결정

| 결정 | 내용 |
|---|---|
| 좌표 추적 ❌ | 모니터 3개·창 10개+ 환경에서 좌표로 카톡 창 찾기 = **사막 모래찾기**. 채택 ❌ |
| **활성 창 트래킹** | Win32 `GetForegroundWindow` + `pygetwindow.getActiveWindow()` — OS가 알려주는 핸들 |
| 친구추가 팝업 = 메인 창 모달 | mr.와이 환경 검증됨 (별도 윈도우 ❌). 메인 창 비율 좌표로 처리 |
| 친구추가 팝업 위치 박제 | 메인 창 중앙부 (변수 ❌, 절대 변경 ❌) |
| 1:1 대화창 추적 | 친구이름 title 매칭 (검색·검증) — 활성 창 추적으로 자동 위치 감지 |
| 다른 카톡 대화창 ❌ 닫음 | "트리거가 띄운 그 대화창만" 조작 — `close_all_chat_windows` 폐기 |

#### 4중 안전망 (친구추가 팝업 입력)

| # | 안전망 | 동작 |
|---|---|---|
| 1 | Tab x2 | 이름 입력 후 Tab 2번 (1번 = 국가코드 +82, 2번 = 핸드폰 칸) |
| 2 | 마우스 좌표 클릭 | Tab 실패 시 핸드폰 칸 좌표로 강제 이동 |
| 3 | 시야 확장 ±50px | 1·2 모두 실패 시 ±10·20·30·40·50px 위·아래 훑기 |
| 4 | 노란 버튼 색상 검증 | RGB 판별: `B < 100` = 활성(노랑), `B > 200` = 비활성(회색). 실패 → 시야 확장 → 그래도 실패 시 비정상 종료 |

→ 4중 안전망에서도 실패 = `error_code: form_fill_inactive` + 비정상 종료.

#### 검증된 좌표 (메인 창 비율 기준)

| 요소 | 비율 |
|---|---|
| 사이드바 친구 아이콘 | (0.08, 0.05) |
| 친구추가 버튼 (우상단 사람+) | (0.94, 0.07) |
| 검색바 | (0.47, 0.11) |
| 첫 검색 결과 행 | (0.50, 0.17) |
| 팝업 이름 입력칸 | (0.50, 0.4566) |
| 팝업 핸드폰 입력칸 | (0.50, 0.5465) |
| 노란 친구추가 버튼 | (0.73, 0.73) |
| 노란 1:1 채팅 버튼 | (0.41, 0.73) |
| 백드롭 검출 (팝업 감지용) | (0.05, 0.20) |
| 대화창 메시지 입력 영역 | (0.50, 0.85) |

#### 색상 판별 (노란 버튼 활성·비활성)

| 상태 | RGB |
|---|---|
| 활성 (노란) | (242, 233, 54) — B 채널 < 100 |
| 비활성 (회색) | (242, 242, 242) — B 채널 > 200 |

#### 의존성

| 라이브러리 | 용도 |

## §11-L 카톡 자동화 운용 룰 박제 (신설)

**§11-K 다음에 §11-L 신설**:

### §11-L. 카톡 자동화 운용 룰

#### 운용 환경 필수 조건

| 조건 | 답 |
|---|---|
| mr.와이 마우스·키보드 ❌ | ✅ 필수 (자동화 진행 중) |
| 화면보호기·잠금 OFF | ✅ 필수 |
| 카톡 PC앱 실행 + 로그인 + 화면 보임 | ✅ 필수 |
| 카톡 위치 (모니터 1·2·3) | ✅ 무관 — 활성 창 트래킹 |
| 다른 프로그램 실행 | ✅ 무관 |
| 다른 카톡 대화창 다수 열림 | ✅ 무관 |

#### 시간 운용 룰

| 룰 | 내용 |
|---|---|
| 개별 단계 timeout | 30초 — 그 이상 응답 ❌ 시 불완전 종결 |
| 30초 룰 적용 단계 | 친구추가 팝업 대기 / 검색 후 대화창 진입 / 알림토스트 fallback |
| 알림토스트 fallback | 친구이름 재검색 → 재진입 → 또 모호 시 재검색 → 30초 경과 시 불완전 종결 |
| 고객 간 인터벌 | 10~60초 랜덤 (mr.와이 운용 단위 100명 이내 기준) |
| 텍스트→이미지 인터벌 | 2~6초 랜덤 |
| 친구추가 후 대기 | 2~4초 |

#### 오류 코드 (mr.와이 후속 처리 구분)

| error_code | 의미 | mr.와이 후속 |
|---|---|---|
| `success` | 정상 발송 | ❌ |
| `duplicate_name` | 동명이인 검색됨 | 수동으로 정확한 친구 식별 후 발송 |
| `friend_add_failed` | 친구추가 실패 + 검색 결과 0명 | 카톡 미가입 또는 친구추가 OFF — 다른 채널 검토 |
| `kakao_loading_or_unresponsive` | 카톡 응답 지연 (30초 timeout) | 카톡 재시작 후 재시도 |
| `form_fill_inactive` | 친구추가 입력 4중 안전망 모두 실패 | 카톡 GUI 변경 가능성 — 디버그 캡처 → CTO 패치 |
| `kakao_not_found` | 카톡 PC앱 ❌ 실행 | 카톡 실행 후 재시도 |
| `aborted` | mr.와이 마우스 코너 이동 (FAILSAFE) | 의도적 중단 — 재시도 |
| `unexpected_screen` | 예상치 못한 화면 상태 | 디버그 캡처 → CTO 패치 |
| `exception` | Python 예외 발생 | 로그 → CTO 패치 |

#### 운용 단위·한계

| 항목 | 값 |
|---|---|
| 1회 자동화 단위 | 10~20명 (안정적) — 100명 이내 (확장 시) |
| 보장 사항 | 잘못된 발송 0% / 정상 발송 97~99% / 시나리오 4종 100% 분기 |
| 외부 변수 한계 | 카톡 서버 일시 응답 지연·OS 알림 모달 1~3% — 30초 룰로 자동 종결 |
| 카톡 보안 정책 | mr.와이 인지·인정한 우려 (CTO 통제 ❌) |
| 카톡 GUI 변경 | mr.와이 인지 — 디버그 캡처 → CTO 즉시 패치 (운용 단계적 복원) |

#### 자동화 표준 흐름 (§11-H 보강)

| # | 단계 | 주체 |
|---|---|---|
| 1 | 고객 정보 dataN.txt → input 폴더 (1명 1파일) | mr.와이 |
| 2 | 본 채팅 CTO 명령어 요청 | mr.와이 |
| 3 | CTO 명령어 작성·제공 | CTO |
| 4 | 클로드코드 복붙 → 실행 | mr.와이 |
| 5 | 자동화 진행 (PC ❌, 약 N×30초) | 자동 |
| 6 | output 산출물 (PNG·메시지·로그) + 사유별 오류 통계 | 자동 |
| 7 | output 산출물 토스인슈1 클로드 첨부 → "자동화결과 보고해줘" | mr.와이 → 토스인슈1 |
| 8 | 검증 보고 → CTO 결과 공유 | mr.와이 → CTO |

#### 디버그 절차 (오류 발생 시)

| 단계 | 동작 |
|---|---|
| 1 | `output\debug\` 폴더 캡처 자동 저장 (매칭 실패 시) |
| 2 | mr.와이가 캡처를 본 채팅에 업로드 |
| 3 | CTO 즉시 진단 + 좌표·로직 패치 |
| 4 | mr.와이 파일 재배치 + 재실행 |

### ⓥ 새 대화창 이전 워크플로우 (페르소나 격리 + 단일 책임 보장)

> **본 룰은 모든 페르소나(L1·L2·L3)에 동일 적용된다. 감지·안내는 활성 페르소나, 이전 준비는 L1 단독 — 페르소나 격리(ⓡ) + 단일 책임(§1.3) 동시 충족.**

|---|---|---|

| ⓥ-2 (이전 준비) | mr.와이 동의 발화(동의어 일체 — "응"·"네"·"그래"·"이전 준비해줘"·"넘어가자"·"옮기자" 등) → **활성 페르소나가 L1 개발총괄로 전환** (§7.1 시그널 발화 불필요 — ⓥ-2 동의 자체가 시그널) | 3종 산출물 생성 (ⓘ): 인스트럭션·zip·통합업무파일. worklog·02_summary 갱신 (직전 활성 페르소나·작업명·상태 박제). 본 대화창은 L1 상태로 종료 |
| ⓥ-3 (새 대화창 자동 안내 + ⓨ 정합 검증 + 검토 보고) | 새 대화창 첫 진입 — L1 개발총괄 (§1.1 박제 룰) | mr.와이 첫 발화가 무엇이든 (인사·질문·아무 말 등) L1 자동 발동: **(1) ⓨ 정합 자체 검증** (메타룰 항목 수·합의 항목 수·worklog 박제 카운트·통합업무파일 정합 카운트) → **(2) worklog·02_summary 확인** (직전 활성 페르소나·작업·박제 대기 인지) → **(3) 검토 보고 출력**: "새 대화창 검토 보고: [정합 검증 결과 — 항목 수·불일치 여부] / [직전 활성 페르소나·작업명·상태] / [박제 대기·미확인 추적 사항]. [활성 페르소나]로 변경하여 이어가시겠어요?" **검증 불일치·결함 발견 시 정직 보고 의무 (ⓤ 6번·7번 강화).** 본 메시지는 §2.1 첫 응답 룰 본문이며, §2.2 일반 진입 룰을 확장 대체한다 (이전 직후 새 대화창 한정). |
| ⓥ-4 (페르소나 복원 제안) | mr.와이 동의 발화 ("그래"·"응"·동의어 일체) | L1 → 활성 페르소나 전환 → 작업 이어감. 거부·다른 작업 지시 시 L1 유지 |
